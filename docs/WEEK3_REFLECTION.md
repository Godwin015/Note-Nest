# Week 3 Reflection – NoteNest

## 1. Introduction

During Week 3 of the NoteNest project, I focused on improving the notes management module, strengthening backend security, implementing search and filtering functionality, and investigating database and frontend performance.

The work involved backend and frontend development using Laravel, React, TypeScript, and MariaDB.

This week provided an opportunity to go beyond implementing application features and examine how the application behaves under different conditions. An important part of the experience was learning to identify performance concerns, investigate their underlying causes, implement appropriate solutions, and verify the results.

### 2.5 Frontend Performance Optimization

During production-build verification, Vite initially reported that the main JavaScript bundle exceeded its default 500 kB chunk-size warning threshold.

I investigated the bundle composition and identified the rich-text editor and its Tiptap dependencies as a substantial contributor.

To address this, I:

- Extracted the rich-text editor from `NoteNestApp.tsx` into `NoteEditor.tsx`.
- Used React `lazy()` to load the editor as a separate JavaScript chunk.
- Used `Suspense` to provide a loading fallback while the editor is being loaded.
- Updated the editor's content synchronization to preserve HTML when creating and editing notes.
- Re-ran ESLint and the frontend automated tests.
- Generated a new production build to verify the optimization.

The final build completed successfully without the previous chunk-size warning.

## 3. Challenges Encountered

### 3.1 Frontend Search and Category Filtering

One challenge was ensuring that search and category filtering worked together without one operation unintentionally resetting the other.

The dashboard initialization effect was also causing filter state to be overridden through repeated loading.

This was addressed by maintaining a reference to the latest `loadNotes` callback and adjusting the initialization effect so that it would not repeatedly reset the dashboard filters.

Browser verification subsequently confirmed that search and category filtering work together and that clearing search preserves the selected category.

### 3.2 Search Debouncing

Sending an API request on every keystroke can generate unnecessary network traffic.

To address this, I implemented a 400ms debounce using `setTimeout` and `clearTimeout`.

This ensures that the search request is sent after the user pauses typing rather than immediately after every character.

I also implemented timer cleanup to prevent pending search operations from running unnecessarily.

### 3.3 Authorization and Data Privacy

Another important challenge was ensuring that users cannot access another user's private notes.

The solution involved scoping note queries through the authenticated user's relationship and testing unauthorized access attempts.

The authorization tests were strengthened to verify not only that unauthorized requests return HTTP 404, but also that the original note remains unchanged after attempted updates and deletions.

This reinforced the importance of enforcing security at the backend rather than relying on frontend restrictions.

### 3.4 Database Query Performance

During the database investigation, some queries performed table scans even though relevant indexes existed.

The investigation showed that the database optimizer selected a table scan on the small development dataset.

This helped me understand that the presence of an index does not guarantee that the database will use it.

I also learned that a conventional B-tree index is generally not effective for arbitrary substring searches using a leading wildcard, such as:

```sql
LIKE '%keyword%'
```

The investigation helped distinguish between an index being available and an index actually being selected by the database optimizer.

### 3.5 Date Filtering

The initial date-filtering implementation used `whereDate()`, which applies a database date function to the timestamp column.

I changed this to direct date-range comparisons to make the query more suitable for index usage.

This was an important learning experience in writing database queries with indexing considerations in mind.

Although the new approach is more index-friendly, I did not claim a measured performance improvement because a controlled benchmark was not conducted.

### 3.6 Frontend Bundle Size and Code Splitting

One of the major frontend optimization challenges occurred during the production build.

The initial Vite build generated a main JavaScript bundle of approximately 877.03 kB, resulting in a chunk-size warning.

Rather than simply increasing Vite's warning threshold, I investigated the application dependencies and identified the rich-text editor as a substantial contributor.

I extracted the editor into a separate component and implemented lazy loading using React `lazy()` and `Suspense`.

The refactoring initially introduced issues involving asynchronous editor initialization and content synchronization. In particular, existing plain-text content needed to be normalized into HTML before the parent component submitted it.

I addressed these issues by updating the editor initialization and content synchronization logic.

After the changes, all 12 frontend tests passed, ESLint completed successfully, and the production build completed without the previous chunk-size warning.

This challenge taught me the importance of verifying both performance improvements and functional correctness after refactoring.

## 4. What I Learned

The following are my major technical lessons from Week 3:

1. **Authorization must be enforced at the backend.** Frontend restrictions alone are insufficient to protect private user data.

2. **Automated tests should verify application behaviour and data integrity.** It is not enough to test only HTTP response codes.

3. **Database filtering should happen at the database level.** Retrieving all records and filtering them in application memory becomes inefficient as datasets grow.

4. **Debouncing improves search interaction.** It reduces unnecessary API requests while maintaining a responsive search experience.

5. **Indexes do not guarantee faster queries.** The database optimizer considers the query, available indexes, and estimated execution cost when selecting an execution plan.

6. **Leading-wildcard searches have performance limitations.** A conventional B-tree index generally cannot efficiently support arbitrary substring matching.

7. **Date-range comparisons can be more index-friendly than applying functions to timestamp columns.**

8. **N+1 query problems should be investigated using actual query behaviour rather than assumptions.**

9. **Performance claims should be supported by evidence.** An `EXPLAIN` result alone does not establish that one implementation is faster than another.

10. **Code splitting improves frontend loading strategy.** Separating large dependencies into lazily loaded components can reduce the amount of JavaScript required during initial application loading.

11. **Refactoring requires functional regression testing.** Moving a component into a separate file can introduce initialization, state synchronization, and asynchronous loading issues.

12. **Performance optimization should not compromise functionality.** The editor extraction was followed by automated testing to ensure that note creation, editing, and other existing features continued working.

## 6. Areas for Further Improvement

Although the Week 3 implementation passed its automated tests and the identified frontend bundle issue was resolved, there are areas I would improve in future iterations.

- Benchmark database queries using a larger and more representative dataset.
- Evaluate MariaDB FULLTEXT search if substring search becomes a performance concern.
- Review index usage as the notes dataset grows.
- Continue monitoring database query counts and attachment retrieval patterns.
- Expand frontend tests to cover additional combinations of filters and edge cases.
- Expand browser-based regression testing to cover additional rich-text editing scenarios and edge cases.
- Monitor frontend bundle sizes during future production builds.
- Investigate further code splitting only where bundle analysis demonstrates a clear benefit.
- Introduce performance monitoring and profiling to support evidence-based optimization decisions.
