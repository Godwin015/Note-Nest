# Search Performance Investigation – NoteNest

## 1. Overview

This document records the database query investigation and performance optimization work conducted during Week 3 of the NoteNest project.

The investigation focused on understanding how Laravel retrieves, searches, filters, sorts and paginates notes, as well as identifying opportunities to improve database and frontend performance.

The key areas examined were:

- Laravel Eloquent query behaviour.
- SQL queries generated by the application.
- Existing database indexes.
- Query execution plans using MariaDB `EXPLAIN`.
- Keyword search performance.
- Date filtering and sorting operations.
- Attachment retrieval and potential N+1 query problems.
- Frontend JavaScript bundle composition and code splitting.
- Opportunities for future performance improvements.

The objective was to investigate actual application behaviour, apply appropriate optimizations and document the findings without making unsupported performance claims.

## 2. Database Environment

The investigation was conducted against the local development environment.

| Component | Technology |
|---|---|

**Investigation limitation:** The database contained a relatively small dataset during testing. Therefore, the observed execution plans may differ from those produced by a larger production database.

## 3. Existing Database Indexes

The existing indexes were inspected using:

```sql
SHOW INDEX FROM notes;
```

The following indexes were identified:

| Index | Columns |
|---|---|
| PRIMARY | id |
| notes_is_pinned_updated_at_index | is_pinned, updated_at |
| notes_category_index | category |
| notes_user_id_is_pinned_updated_at_index | user_id, is_pinned, updated_at |

The attachment table was inspected using:

```sql
SHOW INDEX FROM note_attachments;
```

The following indexes were identified:

| Index | Columns |
|---|---|
| PRIMARY | id |
| note_attachments_note_id_index | note_id |

### 3.1 Index observations

The composite index:

`notes_user_id_is_pinned_updated_at_index`

supports queries that filter notes by user and order them using pinned status and update date.

The category index supports category-based filtering.

The `note_attachments_note_id_index` supports retrieving attachments associated with individual notes.

An additional index exists on `(is_pinned, updated_at)`. It partially overlaps with the composite index. It was retained because further workload analysis would be necessary before determining whether removing it would be appropriate.

No indexes were removed solely on the basis of this investigation.

## 4. SQL Query Investigation

Laravel Eloquent was used to inspect the SQL generated by the application.

### 4.1 Normal note retrieval

The normal note retrieval query follows this structure:

```sql
SELECT *
FROM notes
WHERE user_id = ?
ORDER BY
    is_pinned DESC,
    updated_at DESC,
    id DESC;
```

The user ID is supplied as a parameter.

This ensures that notes are retrieved within the authenticated user's ownership scope and that pinned notes appear before unpinned notes.

The additional `id DESC` ordering provides a deterministic tie-breaker when notes have identical pinned status and update timestamps.

### 4.2 Keyword search

The keyword search query follows this structure:

```sql
SELECT *
FROM notes
WHERE user_id = ?
AND (
    title LIKE ?
    OR content LIKE ?
)
ORDER BY
    is_pinned DESC,
    updated_at DESC,
    id DESC;
```

An example of the search parameters is:

```text
%Laravel%
%Laravel%
```

Search is performed at the database level rather than retrieving all notes and filtering them in PHP.

The user ownership condition is retained alongside the grouped title and content search conditions.

This is important because search results must remain restricted to the authenticated user's private notes.

### 4.3 Date filtering

The initial date-filtering approach used Laravel's `whereDate()` method.

An example of the generated SQL was:

```sql
SELECT *
FROM notes
WHERE user_id = ?
AND DATE(created_at) >= ?;
```

This applies a database function to the `created_at` column.

The implementation was subsequently changed to direct date-range comparisons:

```sql
SELECT *
FROM notes
WHERE user_id = ?
AND created_at >= ?
AND created_at < ?;
```

For example, filtering from November 1, 2026, through November 4, 2026, uses:

```sql
created_at >= '2026-11-01 00:00:00'
AND created_at < '2026-11-05 00:00:00'
```

This approach avoids wrapping the timestamp column in a date function and can make an ordinary index on `created_at` more usable for range filtering.

However, a measurable performance improvement was not established through controlled benchmarking.

## 5. EXPLAIN Investigation

MariaDB's `EXPLAIN` statement was used to inspect the database execution plans.

### 5.1 Normal note retrieval

The following query was investigated:

```sql
EXPLAIN
SELECT *
FROM notes
WHERE user_id = 1
ORDER BY
    is_pinned DESC,
    updated_at DESC,
    id DESC
LIMIT 10;
```

Observed results:

| Property | Result |
|---|---|
| Access type | ALL |
| Possible key | Composite notes index |
| Selected key | NULL |
| Estimated rows | 8 |
| Extra | Using where; Using filesort |

The optimizer selected a table scan rather than using the available composite index.

Because the table contained only a small number of records during the investigation, a table scan may have been considered less expensive than index access.

This observation does not establish that the existing index is ineffective.

### 5.2 Keyword search

The following query was investigated:

```sql
EXPLAIN
SELECT *
FROM notes
WHERE user_id = 1
AND (
    title LIKE '%Laravel%'
    OR content LIKE '%Laravel%'
)
ORDER BY
    is_pinned DESC,
    updated_at DESC,
    id DESC
LIMIT 10;
```

Observed results:

| Property | Result |
|---|---|
| Access type | ALL |
| Possible key | Composite notes index |
| Selected key | NULL |
| Estimated rows | 8 |
| Extra | Using where; Using filesort |

The optimizer again selected a table scan.

One important consideration is the use of leading wildcards in the search conditions.

A conventional B-tree index generally cannot efficiently locate arbitrary substrings using a pattern such as:

```sql
LIKE '%Laravel%'
```

This differs from prefix searching:

```sql
LIKE 'Laravel%'
```

The current implementation prioritizes substring matching in both the title and content fields.

### 5.3 Forced-index investigation

The composite index was also tested using `FORCE INDEX` to understand whether it could be used for the user filtering condition.

The forced-index investigation showed:

| Property | Result |
|---|---|
| Access type | ref |
| Selected key | Composite user/pinned/update index |
| Estimated rows | 5 |
| Extra | Using where |

This demonstrated that the composite index could be used for the user filtering condition.

However, forcing an index does not establish that it provides better overall performance.

No controlled benchmark was conducted to prove that the forced-index query executes faster than the optimizer's original execution plan.

## 6. Search Performance Considerations

The current search implementation uses SQL `LIKE` with leading and trailing wildcards.

Example:

```sql
WHERE title LIKE '%keyword%'
   OR content LIKE '%keyword%'
```

### Advantages

- Supports substring matching.
- Allows users to search note titles and content.
- Performs filtering within the database.
- Retains authenticated-user ownership restrictions.
- Integrates with pagination.
- Avoids loading the entire notes collection into application memory for filtering.

### Limitations

A conventional B-tree index is generally ineffective for arbitrary substring searches beginning with `%`.

As the number of notes grows, substring searches may require examining many records belonging to the authenticated user.

### Possible future improvements

For larger datasets, the following options can be evaluated:

1. MariaDB FULLTEXT indexes for title and content searching.
2. A dedicated search engine if search requirements become more complex.
3. Benchmarking prefix search against substring search where product requirements permit it.

FULLTEXT search should not be introduced without evaluating its matching semantics because it may behave differently from the existing substring-search implementation.

## 7. N+1 Query Investigation

The note and attachment retrieval workflow was inspected.

The following observations were made:

- The notes dashboard retrieves notes through the notes API.
- Attachments are retrieved separately when the user opens the note-editing interface.
- Attachment previews are loaded when needed.
- The attachment listing endpoint retrieves attachments through the note relationship.
- The attachment table has an index on `note_id`.
- The frontend does not request attachments separately for every note displayed on the dashboard.

Based on the inspected dashboard workflow, no obvious N+1 attachment retrieval pattern was identified.

The attachment upload workflow also performs separate aggregate queries to check attachment count and total file size before accepting uploads.

Uploads are performed sequentially, with a maximum of five attachments per note.

### Future considerations

If attachments are introduced into every note card on the dashboard, eager loading should be considered to avoid unnecessary repeated queries.

Query logging and profiling should also be used to investigate the number of database queries generated during actual application usage.

## 8. Pagination, Filtering and Sorting

The notes endpoint supports database-level pagination and filtering.

The implemented functionality includes:

- Search by title and content.
- Category filtering.
- Pinned-note filtering.
- Creation-date filtering.
- Sorting by title.
- Sorting by creation date.
- Sorting by update date.
- Configurable page sizes, with a maximum of 50 records per page.

The default page size is 10 notes.

Filtering and sorting are performed at the database level before pagination.

This avoids retrieving the entire notes collection into application memory merely to filter or sort the results.

The implementation also maintains a deterministic ordering to support consistent pagination.

## 9. Frontend Bundle Optimization

During Week 3 production-build verification, an initial Vite build reported that the main JavaScript bundle exceeded the default 500 kB chunk-size warning threshold.

The initial build produced a main JavaScript bundle of approximately 877.03 kB, with a gzipped size of approximately 277.68 kB.

Investigation identified the rich-text editor and its Tiptap dependencies as a substantial part of the frontend bundle.

### 9.1 Optimization approach

The rich-text editor was extracted from the main `NoteNestApp.tsx` component into a dedicated component:

```text
resources/js/NoteEditor.tsx
```

The editor was then loaded using React's `lazy()` and `Suspense`:

```tsx
const NoteEditor = lazy(() => import('./NoteEditor'));
```

This introduced code splitting, allowing the rich-text editor to be loaded separately when the note creation or editing interface requires it.

The change was made without removing the existing rich-text functionality.

### 9.2 Functional verification

After the extraction, the following checks were completed:

- ESLint completed successfully.
- All 12 frontend tests passed.
- Note creation continued to work.
- Existing notes could be edited.
- Rich-text HTML was preserved when submitting edits.
- Search, filtering, pinning, deletion and pagination tests continued to pass.
- TypeScript compilation and the production build completed successfully.

### 9.3 Final production-build results

The final production build generated the following assets:

| Asset | Size | Gzipped size |
|---|---:|---:|
| Main JavaScript bundle | 469.00 kB | 147.89 kB |
| Rich-text editor chunk | 408.89 kB | 129.89 kB |
| CSS bundle | 279.80 kB | 42.74 kB |
| Manifest | 0.50 kB | 0.22 kB |

The main JavaScript bundle decreased from approximately 877.03 kB to 469.00 kB.

This represents an approximately 46.5% reduction in the main bundle's uncompressed size.

**Final result:** The production build completed without the previous Vite chunk-size warning.

The rich-text editor remains a separate JavaScript chunk and is loaded on demand.

This optimization improves the initial loading strategy by separating editor code from the main application bundle. It does not eliminate the editor's download cost when the editor is eventually opened.

## 10. Recommendations

Based on the investigation, the following recommendations are proposed:

1. Retain authenticated-user ownership conditions in all notes queries.
2. Retain the composite index supporting user filtering and pinned/update-date ordering.
3. Avoid removing existing indexes without examining their actual usage and workload.
4. Continue using direct date-range comparisons instead of applying date functions to the filtered timestamp column.
5. Evaluate FULLTEXT search if the notes dataset grows significantly and substring-search performance becomes a concern.
6. Monitor database query counts as the application expands.
7. Consider eager loading if attachments become part of the main notes listing.
8. Benchmark database queries with a representative dataset before introducing further indexing changes.
9. Retain lazy loading for the rich-text editor to avoid unnecessarily including its dependencies in the initial application bundle.
10. Monitor frontend bundle sizes during future production builds.
11. Evaluate additional code splitting only when supported by actual bundle analysis and application usage.

## 11. Limitations of the Investigation

The investigation was conducted against a small local development dataset.

The observed database execution plans are not sufficient to establish production performance.

No formal benchmark was conducted to compare query execution times before and after index usage or date-filter changes.

The frontend bundle measurements represent production-build output, not real-user network performance or browser loading-time measurements.

The investigation therefore distinguishes between verified implementation changes, observed execution plans, production-build measurements and possible future optimization opportunities.

## 12. Conclusion

The Week 3 investigation provided a better understanding of how NoteNest retrieves, searches, filters, sorts and paginates notes.

The database investigation confirmed that note queries retain authenticated-user ownership restrictions, keyword search is performed at the database level, and existing indexes support important filtering operations.

It also identified limitations associated with leading-wildcard substring searches and established a more index-friendly approach to date filtering.

On the frontend, the investigation identified an oversized main JavaScript bundle caused in part by the rich-text editor dependencies. Extracting the editor into a separate lazily loaded component reduced the main bundle from approximately 877.03 kB to 469.00 kB and eliminated the previous Vite chunk-size warning.

The final implementation passed ESLint, all 12 frontend tests and the production build.

These findings provide a practical foundation for maintaining and improving NoteNest's database and frontend performance as the application grows.
